# Docs Module

## 模块定位

`docs/` 保存 WishPool 的产品技术设计文档，并作为代码实现、能力验收、模块边界和运行维护的工程共识入口。

## 文件说明

| 文件 | 用途 |
| --- | --- |
| `ARCHITECTURE_DESIGN.md` | 架构设计文档，说明多客户端、自有业务后端、AI/媒体服务、数据、实时同步、隐私安全、部署和可观测性。 |
| `DETAILED_DESIGN.md` | 详细设计文档，说明角色权限、页面、核心模块、PostgreSQL 数据结构、REST/WebSocket API、状态机、奖励规则、AI/媒体和测试策略。 |
| `TECH_STACK_DECISION.md` | 技术决策文档，集中说明各客户端、服务端、AI/媒体、数据和基础设施采用的语言与脚手架。 |
| `VISUAL_DESIGN_DIRECTION.md` | 视觉方向与设计系统基线，说明儿童端、家长端、Web 和后台的气质、颜色、排版、组件和动效规范。 |
| `IMPLEMENTATION_PLAN.md` | 实现计划，把完整产品按工程依赖拆成工作包，说明每个工作包的产出和验收标准。 |
| `CAPABILITY_COMPLETION_CHECKLIST.md` | 完整能力验收清单，逐项记录服务端、客户端、worker、部署和质量保障的缺口与完成标准。 |

## 维护规则

- PRD 变化时，先更新架构文档中的范围、非目标和关键决策，再更新详细设计中的字段、流程和接口。
- 代码落地后，如果目录、模块边界、公共 API、数据模型或事件流发生变化，需要同步更新本文档和根目录 `PROJECT_CODE_STRUCTURE.md`。
- 文档中的接口、集合名和状态枚举应与实现保持一致，避免“文档一套、代码一套”。
